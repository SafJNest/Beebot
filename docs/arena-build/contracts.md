# Arena analytics contract

Status: Phase 2 implementation contract, reconciled with the user request on 2026-10-01. This document supersedes the earlier proposal; it does not amend an accepted ADR.

## Ownership and compatibility

Arena has a separate `ArenaChampionStatistics` root and pure `ArenaChampionAnalyzer.Accumulator`. Standard `ChampionBuildEngine`, `BuildSignature`, statistics, Mongo queries, Tracker, scheduler and Discord presentation retain their behavior. ADR-0006/0012 require the existing standard response; the earlier proposal to replace it is withdrawn.

`Build` remains the shared container. Additive nullable `orderedCore`, `orderedItems`, `orderedAugments` and `paths` describe one Arena core per `builds[]` element, using shared `Build.Choice`, `Build.Core`, `Build.Slot`, `Build.Path`, `Build.Timing` and `StatisticalLeaf`. Standard constructors leave these fields null and omit them from JSON. Existing standard fields and constructors remain readable and unchanged. Arena branches also retain the compatibility fields; their legacy option lists are empty. These new fields are internal until Phase 4. No existing endpoint serves the Arena root.

## Sequences and identity

The Arena core is the entire observed, committed sequence of relevant non-Prismatic purchases, including purchase of `220007`. It is not a first-Prismatic/boots snapshot and has no arbitrary two-item cap. Thus A → B gives `[A,B]`; A → 220007 gives `[A,220007]`. The full ordered numeric ID list identifies the core. Timestamps never identify cores or paths. Boots have their own global statistics and do not enter the core. The existing `Participant.boots` is a historical derived field that Tracker does not clear on undo; use it only as fallback when no attributed purchase of that ID exists in the stream. Surviving purchases or actual final inventory supply membership otherwise, so an undone purchase cannot be resurrected by that stale field. Prismatics have separate global overall and position distributions (1–6); acquiring 220007 does not itself create a Prismatic choice or imply which Prismatic was awarded.

Only directly attributed acquisition events establish order. Final inventory and the existing participant boots field may establish independent choice membership, with no position or time inferred. The parser accepts a caller-supplied immutable item catalog: boots/relevant completed items come from existing `ItemUtils` rules, ignored items are excluded, and Prismatic classification reuses `PrismaticItemClassifier` (including its 447111 exception). Unknown catalog items are counted and omitted. Catalog loading is outside the accumulator.

The parser input explicitly includes `completeItemHistory`. The convenience accumulator `accept(match)` assumes the available stored item-event array is the complete observed stream; a provider that knows it is partial must use `accept(match, false)`. Missing arrays, invalid times, ambiguous attribution or unsupported transitions prevent positional/core projection. The parser cannot detect events silently omitted by an upstream producer. No production source completeness is claimed in Phase 2.

Events sort by timestamp, with original array index breaking ties. Exact duplicate events are removed. Repeated committed non-Prismatic purchases of the same ID retain the earliest acquisition once per participant-game; repeated Prismatic acquisitions retain their distinct observed order, with overall membership counted once per ID. A position leaf counts a choice at most once per participant-game/ID/position. Choices with only final membership have null positions. Positions above 6 are counted as missing position coverage, without discarding independent membership.

## Supported events and transition policy

The current Tracker parser emits `ITEM_PURCHASED`, `ITEM_SOLD`, `ITEM_UNDO`, `ITEM_DESTROYED`, and numeric `item`, `before`, `after`, timestamp and participant reference. It emits no autonomous transformation event. This is a code audit, not production timeline inspection.

- Purchases add the observed acquired ID (`after` if positive, otherwise `item`). A purchase with different positive `before`/`after` IDs is an explicit transformation: the acquired `after` ID is a new historical choice; the earlier purchase remains historical. No identity is inferred from final inventory.
- Sales/destruction do not erase committed historical purchase choices, including consumption of 220007. They do not create new acquisitions or alter order.
- An undo reverses only the immediately preceding attributed non-undo transition when its positive item/before/after IDs identify that transition unambiguously. Undo of a purchase removes that acquisition; undo of a sale/destruction leaves acquisition history unchanged. Repeated or identity-free/mismatched undo is ambiguous, disables core/position projection and omits the potentially reversed preceding purchase from acquisition membership. An undo without reliable time never removes an incompatible acquisition: positive undo IDs suppress only potentially reversed acquisitions of those IDs; an untimed identity-free undo leaves only independently observed final membership. Final inventory membership remains independently valid.
- Unknown event types, conflicting purchase identity, malformed IDs/times and unidentified catalog entries are recorded. Do not invent transformation events or guess an undo target.
- Participant reference 0 is rejected even if a reference map maps it to a real PUUID. Conflicting references, missing actors or multiple numeric references for the same PUUID are ambiguous. Unattributed events are never assigned to a player. They conservatively disable chronology for the affected observation stream; independent final choices remain valid.

The version-1 `arena_evidence.first_prismatic` payload from Phase 1 remains an optional exact first-position signal. It is accepted only for the actual participant and a classified Prismatic; unknown/ambiguous evidence is counted. Its exact ID can contribute without a timestamp. Duplicate/conflicting PUUID references reject the sidecar as they reject events. An exact first signal at or after a contradictory earlier Prismatic purchase is rejected and recorded without overwriting the observed purchase order. It is never inferred from final inventory. Legacy `core_snapshot` is no longer core identity. No writer currently persists `arena_evidence`; that limitation does not block ordinary attributed purchase analytics.

## Populations and sufficient statistics

One input is one full Arena match. Accumulators filter CHERRY and exact full patch, select all participants of the requested champion, validate unique positive participant IDs and PUUIDs, and reject a repeated full match ID before any updates. Two players with the same champion are distinct participant-games. Missing/noncanonical match ID or patch, wrong queue/patch, and duplicate participant identities are rejected before mutation.

Every `StatisticalLeaf` has distinct participant-games, wins, placement sum, valid-placement games and a placement histogram. Win follows the existing Arena contract literally: `participant.win || subTeamPlacement >= 3`. Preserve the observed placement separately; only 1–8 contributes to valid-placement sufficient statistics. Each choice's winrate is wins / its own games; missing data never enters this denominator as a loss.

Each choice stores an explicit `denominator`: global prevalence uses overall champion participant-games, core entries/conditioned slots and paths use core games. A slot also carries its observed population leaf, making coverage inspectable. Overall ID membership is counted once per participant-game even if multiple positions are observed; position counts need not sum to overall counts. `unpositionedGames` counts participant-games with membership but no known position for that ID. `Build.Timing` has `timeSumMillis`/`timeCount`; its mean uses only timed participant-game choices, choosing the earliest valid acquisition for overall membership. Missing time is never zero.

Timeline absence/partiality does not remove overall outcomes, placement, augments, observed boots, or directly observed final item/Prismatic membership. Only core, ordered slots and paths require complete attributable chronology. Augment positions reflect the existing `Participant.augments` list order, including internal gaps; raw Riot slots lost at ingestion cannot be recovered. No augment time is invented and Participant is unchanged.

`finish()` returns a detached immutable snapshot; calls may be repeated or followed by more accepts. Primary distributions are not truncated. One path per complete core retains the observed acquisition sequence; representative size/cardinality and retention remain a prerequisite to persistence in Phase 3.

## Serialization and future persistence

The Arena root carries schema/aggregation versions, champion ID, exact full patch, overall leaf, `builds[]`, global `boots`, `items`, `prismatics`, `augments`, and coverage/reason counters. Structured JSON/BSON uses the shared `JsonCodec`; no second codec, Spring DTO or opaque payload. Phase 2 has no collection writer, Mongo query, cache, queue, endpoint or backfill. There are no existing persisted Arena statistics to migrate. Existing standard documents round-trip with the same fields; new Arena fields are omitted in standard serialization.

Phase 3's planned collection remains `arena_champion_statistics`, deterministic `_id = championId:fullPatch`, separate from `champion_stats` and `champion_builds`. It must reuse the bounded match/event join while delivering matches without timelines; loading catalogs, completeness evidence, persistence, BSON limit/headroom checks and orchestration belong to their existing owners. No phase may write an unmeasured/unbounded document to production. Resolve the standard `champion_stats` versus handbook `champion_statistics` naming discrepancy outside this phase.
